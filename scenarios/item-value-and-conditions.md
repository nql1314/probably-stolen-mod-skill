# 场景：物品价值、真实条件与用途类别

适用：生产定价、质量/纯度、真伪与鉴定、医疗/消费效果、顾客接受资格，或“说明正确但价格/效果不对”。先区分用途类别、真实条件、对外显示和价值阶段。

## 类别与条件

`GetGameItemType` / `IsGameItemType` 一类用途类别参与顾客需求、违禁品与槽位准入；名称、外观、效果描述或自定义标签不能替代原生类别。从已核对的模板创建时保留所需类别，清除模板专属且不适用的行为，再添加内容自身类别并读回。不要复制图像后假定物品已经属于医疗、食品或其它用途。

需要判断真品、纯度、可用性或药效时，读取目标实例启用的原生真实条件；区分 `realCondition` 与伪装/鉴定后给玩家看的条件。同一 ID 可能有不同真伪和状态。既有条件缺失或冲突时明确拒绝或按本玩法定义处理，不能一律视为最高品质。

消费扩展还要核对原生是否已扣物、治疗、增加状态或触发事件；只加本方负责的结果，防止同时走原生与扩展效果。按实际生效条件读取效果数值，不用 Tooltip 所见价值驱动真实恢复。

## 价值阶段

先追踪价格消费者读取的是工厂默认值、实例内在价值、生产基础价值、品质后价值还是市场/交易价。下游生产或恢复规则使用哪个阶段由内容玩法确定，不能把市场溢价或同一品质奖励反复计入下一轮。

使用 Forge 时：

- 从批次实际消耗的 `Items` / `Liquids` 读取数量与价值；部分消耗只计已取走部分，保留的容器是否计成本由配方规则决定。
- `ForgeProductionValueApi.Calculate` 与 `PerOutputWithOverhead` 等只按当前契约计算。整批成本、加成、产量和取整顺序应有唯一来源；工厂默认售价不自动成为低成本生产的保底价。
- 需要保存品质前价值的自定义产物用 `SetBasis` / `ReadBasis`；写后核对有效状态。只改 `unitValue` 或基础标签，可能在原生重算/读档后失效。
- 原生金属锭等已有纯度定价链的物品，先确认是否应完整保留原生定价。不能给全部产物无条件写生产基价来覆盖纯度差价，也不能同时把品质写入基价再加一次原生品质。
- 液体的体积、各组分实际价值与品质前价值一起转移、混合和回滚。相同总毫升不代表组成或价值相同。

## 实例保存与迁移

复制、移动、独立库存图编码和恢复都要保留真实条件、UID、基础价值、独立特征、耐久及嵌套库存。只保留物品 ID 和数量不能证明恢复出原物品；图 JSON 也不必然包含完整原生特征，见 [存档](save-state.md)。

已有物品是否补写新字段或重新定价由迁移需求决定。不要因新工厂默认值变化就批量改旧物品，更不能通过重抽真伪/品质掩盖缺失状态。

## 验证

针对受影响的真伪/品质档位、部分投入、低成本与循环加工核对数值；保存恢复后再次读取实例条件和实际原生价值。领域公式检查与 Tooltip 检查分别只能证明各自范围；最终交易价、消费效果和原生定价还需对应游戏内证据。
