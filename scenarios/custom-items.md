# 场景：添加游戏物品

适用：新食物、普通物品、模块、容器、带窗口的机器，以及把它们接入商店、掉落、交易或初始物品。物品“能从目录创建”和“玩家能取得并正确使用”是两项独立工作。

## 选择注册方式

| 当前项目条件 | 路径 |
| --- | --- |
| 已有声明式内容运行时 | 按已安装运行时的 schema 写物品数据、图像和依赖版本；先校验 schema/API，再验证实际加载 |
| 需直接接入游戏目录 | 在对应目录初始化后注册独立工厂；候选入口有 `FoodItemDirectory.InitDirectory`、`MiscItemDirectory.InitDirectory`、项目已有的 `OnModItemDirectoryInit` 等 |
| 原目录不支持该类型 | 核对 `DirectoryMaster.Item` 等解析入口的完整签名，仅对自身 ID 返回自建对象；其他 ID 原样交回游戏 |

## 创建步骤

1. 定义带命名空间的稳定物品 ID，选食品/普通/模块/容器/机器目录，写明价格、标签、形状、可堆叠性、可接受槽位和所需资源。查重后注册；不要每次目录重建都盲目 `Add`。
2. 从当前构建已验证的同类模板或工厂创建**新实例**，复制必要外观和形状，随后初始化自己的值与可变字段。避免与模板共享标签集合、槽内容或其它可变状态。
3. 图像见 [图像示例](sprites-and-icons.md)。物品模型的 sprite、背包元素的显示 sprite 和某些解析器缓存可能是不同入口；创建后及读档重建时都检查实际外观。
4. 依需求选择获得路径：商店补货回调、拾荒生成、配方产出、交换奖励或新局发放。要接入拾荒/垃圾堆时读 [掉落表示例](loot-tables.md)。每条路径先检查目录已注册、库存/顾客/场景就绪，再核对游戏原生接受条件和写后落点。
5. 物品自身可保存的品质、耐久或升级状态放在隔离命名空间的标签中，并在读档时处理缺字段/旧版本。不要只在内存缓存中保存会影响售价或效果的状态。

## 类型特有检查

| 类型 | 额外要核对 |
| --- | --- |
| 食品/饮品 | 食物类别、保鲜状态、饮品/液体属性、客户购买标签 |
| 模块 | 可安装槽、属性或效果生成、同类模块的加载/保存路径 |
| 容器 | 内部库存、形状/尺寸、所有权、容器嵌套与 UI 窗口 |
| 机器 | 电池/材料槽、运行周期、读档窗口恢复；继续读 [机器示例](machines-and-recipes.md) |

## 验证

在目录中按 ID 查询、创建一件、放入合法库存、保存重载、执行目标用途；再检查错误 ID、重复初始化、满库存和资源缺失。图标存在或目录里能查到 ID，都不能单独证明物品可用。
