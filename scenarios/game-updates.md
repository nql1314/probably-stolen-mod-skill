# 场景：游戏更新与旧 Mod 适配

适用：Steam 更新后重新编译、排查失效钩子、接入新增系统，或旧资料与当前接口不一致。只核对本次受影响的能力，不因更新而重做全部 Mod。

## 确认各份证据属于什么版本

| 证据 | 用途与边界 |
| --- | --- |
| Steam manifest 的 AppID、分支、`buildid` | 确定磁盘安装版；Demo、Playtest、正式版分别核对 |
| 游戏内部版本/存档预览版本 | 识别游戏数据口径；旧档记录不自动代表当前进程 |
| 启动日志的 `Application.version` | 记录程序自报版本；多次更新可能仍相同 |
| 编译引用的互操作程序集与框架 | 确定实际可编译接口；路径与生成记录必须对应目标游戏 |
| 本次启动时间、加载路径与适配日志 | 确定运行进程实际加载的产物及能力 |

游戏在运行中完成磁盘更新或替换 Mod 时，进程与磁盘可能属于不同构建。没有本次启动证据时保留未知，不擅自退出用户正在玩的游戏来核实。普通适配开发也不自动启动游戏生成新接口。

本地指南、旧验证记录和框架说明中的“当前版本”先看日期与范围；它们是定位入口。当前声明类型和调用者决定接口形态，目标构建的实际运行证据决定行为。官方公告适合确认新增玩法与发布范围，不能替代签名、数值或保存检查。

## 按受影响调用链适配

1. 确认目标构建的互操作程序集已准备好，检查实际项目引用路径。旧程序集仍能编译不能证明新游戏兼容；接口尚未生成时说明缺口，不偷偷沿用旧文件。
2. 沿功能检查声明类型、基类、字段、完整方法签名和调用顺序。编译器生成的闭包编号/捕获字段、库存恢复方法及具体派生实现都可能变化；优先用当前公开辅助方法或 Forge 适配，不沿用历史编号。
3. 再核对方法体语义、返回值、夜结阶段、保存窗口及新增原生副作用。签名不变也可能改了行为，特别要检查原生是否已经实现旧补丁所补的功能，避免再次发物、扣费或结算。
4. 直接地址/偏移写入需要匹配构建与完整签名；Harmony 目标还需确认有实际可用的方法体。失配时停用依赖该入口的功能，保留能独立工作的内容；不要全局吞异常或循环猜字段。
5. 运行已有相关签名/领域检查并编译受影响项目。Forge 公共契约变化时同步调用者、示例和发布引用；需要安装或原生执行时另按 [构建与验证](build-and-verification.md) 的请求边界处理。

不以“改了 Build 常量”“补丁类存在”“相关项目编译通过”宣布整体适配完成。说明已核对的接口、受影响能力与缺失的游戏内证据。

## 本轮维护基线

2026-10-20 核对的本机 **Demo AppID `4349200`，Steam Build `26017150`** 已包含水产养殖；启动日志仍自报 `0.46D`，本轮未重新确认内部版本字符串。这是有日期的本机基线，后续使用仍重读目标环境。

这次接入经验包括涡轮增压器闭包/电池字段变化、水培模块库存恢复入口变化。只在相关功能中检查对应调用链，不把旧闭包名或水培专用恢复方法写成永久契约。
