# 场景：自定义机器、配方与加工

适用：注册可摆放机器，增加电池/材料/产物槽，执行即时或跨夜加工，或给已有机器增加升级与液体处理。

## 内容与运行逻辑分开

定义机器物品 ID、模板、槽位类别、容量/功耗、配方输入、输出、时间、解锁条件和图像。项目已有声明式内容运行时就先用其 schema；只有加工步骤、界面或原生 API 不足以表达时才加 C# 行为。资源和引用 ID 在运行前统一校验。

## 创建机器

1. 等目标目录初始化后注册工厂，基于当前构建已验证的机器模板创建独立实例。建立内部槽、窗口、回调和可保存标签，检查形状、所有权、模块/电池限制。
2. 若窗口会在读档时重建，恢复槽和按钮绑定；避免旧 Unity 引用被继续使用。自定义窗口可参考 [界面注入示例](ui-injection.md)。
3. 把机器状态按“物品实例”保存，不能只按机器类型 ID 缓存。升级上限、耐久、进度和容量统一使用明确单位。

## 一次加工的执行顺序

先只读检查机器仍存在、配方解锁、材料数量、目标容量、电量/燃料、输出落点。确定全部可满足后再执行消耗与产出，并逐步核对实际返回值；游戏 API 无事务时准备失败补偿或可重试的待交付记录。预检与写入之间若库存或机器状态变化，就废弃旧计划。跨夜加工先观察真实调用顺序，选能让完整结果进入本次存档的合法结算点，按“存档槽 + 周目 + 过夜转换 + 机器实例”去重；跨越日计数改变的两个回调必须映射到同一转换。

动作通知未必表示成功生产。只有材料、能源、输出和原生工作资格都证实本批完成，才触发一次工作效果；跳过、失败、重入和读档恢复不得重发。机器按实例分别记录本晚已检查、已提交或待恢复；正常的部分加工进度与失败恢复态应分开。

液体处理要先确认原生体积单位、质量分类和混合组成，再写清 ml/L 转换、来源所有权、过滤前后污染量和滤芯耐久；不能用评分或 UI 文案猜测原生可用性。失败补偿须恢复实际组成和体积，不能以等量的另一种液体代替。机器升级的材料消费遵循 [交互示例](item-interactions.md)。

## 验证

新建、摆放、加工、断电、材料不足、产物槽满、保存重载、跨夜重复回调；读回材料、输出、能源、机器进度和工作效果。对液体再核对单位、混合组成及失败补偿。纯规则检查与配方可解析都不能证明原生消耗、产物交付或存档闭环。
