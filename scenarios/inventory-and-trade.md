# 场景：库存移动、整理、补货与交易

适用：将物品放入容器、排序、向客户柜台补货、调整商店库存或交换奖励。这些路径会改变所有权和落点，必须以游戏实际接受结果为准。

## 库存移动

若需求只是观察物品放入 Inventor 库存，先核对 `ModHook.OnPlaceInventorInventoryItemEarly/Late(Action<List<GameItem>>)` 的调用位置和传入列表；它不是所有库存移动的通用事件，不能据此判断任意容器已接纳。真正写入或交易仍按下述接纳结果核对。

1. 确认源库存、物品稳定身份、玩家所有权、`MayRemove` 一类移除条件、目标容器规则、形状与空间。拒绝来源不明、目标不可保存或会导致非法嵌套的物品。
2. 优先使用当前构建的原生单次接受方法，例如 `GraphUtils.TryAcceptOnce` 的对应重载；先核对它对部分接受、剩余量与所有权的语义。写后读回源/目标，区分完整移动、部分移动、复制、拒绝和恢复失败。
3. 批量移动逐件执行并设上限；记录已成功项，遇到不可恢复的失败即停，不把整批报告为成功。拖放路径先处理一次性令牌，详见 [交互示例](item-interactions.md)。

## 整理网格

对当前可见且允许整理的库存生成快照，记录每件物品的稳定身份、原库存、坐标、方向和真实形状 mask；固定不应移动的容器。只在快照上规划，全部物品都有合法落点后再提交。布局搜索必须限制候选数、步数、内存和单帧耗时；复杂库存要分帧计算或提前终止，不能在输入回调里同步搜索数秒。跨帧计算期间库存一旦变化，就丢弃旧方案；Unity 对象的读写仍在主线程执行。

提交前复核库存与快照一致。使用当前构建已验证的暂存/移出方式先清出待移动物品，再逐件放入目标位置；不能让新位置与尚未移走的旧物品相撞。逐步检查移出与 `PlaceItem`/等效方法的结果，最后核对物品集合、数量、归属、坐标和方向。失败时先清理部分新布局，再尝试按快照恢复并重新验证；若恢复也失败，停止后续写入，记录未恢复物品及其落点，不能报告为已回滚或排序成功。没有安全暂存和恢复路径时不要执行批量整理。

## 客户与商店

| 需求 | 关键检查 |
| --- | --- |
| 增加商店货物 | 只在目标商人/补货阶段执行；查目录、限库存数量、避免重复补货和递归触发 |
| 向交易台补货 | 确认当前客户、预算有限且足够、台面未锁定、物品符合购买偏好，并复用原生接纳条件 |
| 交换/购买材料 | 先检查资格、余额、库存空间和材料数量；扣除后确认奖励交付，失败需保留待交付状态或补偿 |
| 改客户预算/议价 | 优先在特定客户创建或价格计算点做窄范围调整；规则见 [数值示例](gameplay-rules.md) |

## 验证

正常交易、余额不足、库存满、部分接纳、客户离场、读档与重复按钮触发；逐项核对现金、材料、源/目标库存和商店货物。整理还需检查互换位置、搜索超限后库存不变、提交中途失败及恢复失败的报告。原生方法被调用不等于交付完成。
