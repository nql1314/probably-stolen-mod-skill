# 场景：保存物品状态与周目进度

适用：物品品质/升级、一次性奖励、机器进度、每日计数、角色排期、独立数据文件或存档备份。先确定状态属于物品实例、存档槽、周目、游戏日还是全局偏好。

## 选保存位置

| 状态 | 优先位置 | 注意 |
| --- | --- | --- |
| 某件物品的品质/升级 | 游戏可保存的物品 tags/字段及原生特征 | 带命名空间键和格式版本，核对原生有效状态与复制行为 |
| 周目进度与待交付奖励 | 游戏支持的 `PlayerStore.modData` 或等效存档扩展点 | 用存档槽 + 周目 ID 隔离，缺字段与旧版本回退 |
| Forge 内容 Mod 的周目 JSON | 当前 `ForgeRunDataApi.Read / Stage` | 只读取或比较后暂存所属记录，实际文件保存与读回另行确认 |
| 隐藏库存与完整物品图 | `ForgeInventoryEndpointApi` / `ForgeSaveGraphApi` | 同时保留 UID、子库存拓扑、原生特征与有效条件，见 [库存](inventory-and-trade.md) |
| 用户范围设置 | MelonPreferences 或项目配置 | 不存一次性发放记录、未完成交易等周目状态 |
| 必须独立的文件 | 项目约定的 UserData 路径 | 文件名含槽/周目身份，先验证新内容再替换旧内容 |

## 生命周期

真正新局生成初始状态；读档迁移/恢复；保存前序列化并检查可写性；切换存档槽和场景时清空旧对象缓存。格式中写 `version`，读取时分别处理已知旧版、可补缺字段、损坏和未来版本。身份失配、损坏与未来版本保留原数据并停用相关写入，不能重新建空状态。对外部数据限制文件大小、条目数和嵌套深度；只在已确认有完整有效旧数据时回退，不用半份解析结果覆盖用户文件。

项目采用周目 `ConfigSnapshot` 时，在新局创建一次并随正确周目保存；读档继续使用已保存规则，不因新的编译默认值自动改写。需要迁移时单独定义版本和结果，见 [配置](config-and-localization.md)。

一次性行为记录“待执行 → 已写入游戏结果 → 已确认完成”，失败时保留可重试状态。跨游戏存档与外部文件的写入没有共同事务；设计保存顺序、稳定操作 ID 和崩溃后对账，使重复执行不会重复扣款或发奖。首次存档涉及新槽位时还需核对槽位分配和失败清理，见 [自定义开局](custom-starts.md)。

向 `modData` 或扩展 API 写入内存，只说明数据已暂存；调用保存方法，也只说明请求已发出。确认实际保存完成后，从目标槽回读并核对槽位、周目、版本和关键结果，再标记持久完成。保存结果不明时先对账，不自动重做可能已扣款、消耗或发放的动作。

使用 `ForgeRunDataApi.Stage` 时同时传入当前 run/slot 与预期旧 JSON；`expectedJson = null` 表示该键必须不存在。冲突后重新读取并判断，不能无条件覆盖。生命周期 After 仅表明对应原方法主体执行过，缺文件等早返回仍可能触发；外层流程正常结束也不能证明内层保存未被其它前缀跳过。真实加载晚期事件与目标文件回读分别确认。

## 旧周目另存新槽

原生 `InitialSave` 可能被已有周目用于分槽，并在分配新 run/slot 后嵌套 `SaveGame`；不能将每次调用都当新开局。区分原生寻址身份与内容的逻辑周目身份：分槽继承现有进度、随机状态、物品 UID、交易和领奖收据，不重新发开局物品。

框架已有 `ForgeRunForkApi` 时，按当前 `docs/RUN_FORK_COMPATIBILITY.md` 注册所属状态并保留 lease：

- `rebind` 是纯转换，先验证来源，再只修改原生寻址字段；不能发物、扣费或保存。格式损坏、未知版本及未完成交易按内容契约拒绝分槽。
- `ready` 在分配槽位前拒绝忙碌事务；`rebound` 只重绑会话并失效旧回调，不重新加载物品图、商人货物或执行交易。
- 一次性发放先检查 `IsForking`。收据随实际结果一起保存；奖励后来卖掉、移走或销毁不意味着可以再领。
- 迁移在内层保存的内容序列化之前完成，不能拖到 `InitialSave` 后置回调。保存后核对目标槽身份及登记的完整 JSON；分槽后失败时阻止会话继续写入并重新载入来源，不能猜测修复索引或自动重试。

已失配旧分支只通过用户本次选择且可验证的来源快照执行显式恢复。`RepairFromSnapshot` 要求已登记状态与来源完整匹配并通过提供者验证；`ReboundInMemory` 仍不代表写盘。普通读档不自动调用恢复入口，不凭相似 ID 合并不同周目的记录。

## 任务包含存档备份或恢复时

备份应在游戏确认保存完成后执行，按槽位与日期命名，设置有限保留数。复制前确认当前槽位的必需文件及相关共享索引已写完；先写临时备份并校验完整性，再发布、更新“当日已备份”标记和裁剪旧备份。只裁剪已确认完整且属于该槽位的旧备份。恢复前检查文件完整性和校验值，保留原存档副本；跨多个文件恢复时记录待恢复状态与回滚材料，并处理恢复中途退出后的再次启动。恢复后实际读档验证，不能只凭复制成功宣布可用。

这些要求用于实现备份功能或覆盖重要存档；常规代码/文档修改不创建 `.bak`、整目录副本或哈希报告。

## 验证

按改动选择保存重载、换槽、新局、旧格式和部分失败。分槽还核对新身份下完整进度与收据不丢、不重领；完整物品图核对原 UID、子库存、真实条件和价值。一次性奖励同时核对库存/现金与收据。离线字符串序列化或托管 stub 不能证明真实 ES3 图和新进程恢复；未执行时明确保留原生验收项。
