# 场景：玩法设计与技术可行性

适用：提出新 Mod、评审设计、把参考玩法转成开发方案，或判断现有接口能否实现。先读相关原生机制与项目已有内容，规划请求不自动进入开发。

## 从游戏中的经营选择出发

明确玩家从哪里取得材料，如何处理/持有，交给谁或用于什么经营目标，以及现金、占格、时间和维护的代价。不要仅因原作有某类道具就添加战斗或另一套成长系统；用户指定无战斗、独立 Mod 或限制物品数量时按其范围设计。

先核对原生目录、顾客需求、网络解锁、商人排期、加工、夜结和保存入口中与需求有关的部分。已有 Mod、未完成设计和发布目录都可能占用同一玩法或 ID；需要避免重叠时检查这些内容。用户要求不与公开 Mod 重复时，另核对可访问的当前列表，并说明已核对范围，不能把本地目录当作完整线上审计。

借鉴其它游戏时先理解被借用的决策，再映射到本游戏：例如材料用途分支、目标反推和库存取舍。不要顺带搬入不需要的战斗、完整合成循环或大量品质词条。

## 在实现前确定会影响结果的规则

| 规则 | 需要说清 |
| --- | --- |
| 玩家选择 | 首版保留哪些有后果的选择；哪些继续复用原版操作 |
| 输入与资格 | ID/用途类别、真实条件、所有权、数量、解锁与可用位置 |
| 数值与时序 | 单位、取整、每日/每批次数，效率/性能/质量各影响什么 |
| 消耗与交付 | 扣费/扣料和产出的顺序，满库存、拒收、部分完成的处理 |
| 状态与恢复 | 物品实例、游戏日、逻辑周目或全局；读档、旧档与分槽如何处理 |
| 接入能力 | 已有公共 API、可复用原生行为、需要新增的窄范围适配 |

不为了补齐表格虚构规则；能由现有契约确定的直接确定。真正影响玩法或数据安全且无法推断的缺口，先指出再请用户定夺。小型修改只核对受影响的规则，不要求重写整份设计。

## 判断可行性

分别标记已确认接口、设计假设和待游戏内验证项。注册成功不等于可取得，商店出现不等于顾客接受，内存 JSON 可写不等于完整物品图能保存。

内容 Mod 持有具体配方、价格、业务状态和资源；公共框架持有通用注册、生命周期与已有事务。需要新框架能力时先说明缺口与最小契约，不在内容侧复制内部实现，也不凭接口名承诺尚未提供的原子操作。

首版按最小完整经营循环划范围，保留与本次风险相关的验收条件。供应链、唯一制造、跨库存或长周期玩法，先把一条实际闭环及失败恢复做实，再扩展更多品类或店铺；不预建假想兼容层、额外菜单或发布流程。

交付保留用户最终采用的名称、ID、中文措辞与规则；若规则被修正，同步公式、声明、文案和验收，不保留会继续驱动旧行为的双重规则。
