# 库存、交易与资源事务

适用于整理、拖放、批量加工、升级、支付与奖励。先确定权威入口的前置条件、返回值含义、是否移动原对象、是否允许部分接受及是否维护原生索引；不能由函数名推断。

## 预览与提交

UI预览只产生候选计划。最终提交时重新读取当前物品、归属、数量、条件、余额、目标容量和原生资格；尤其是拖动途中按键改变、目标换位、材料被消耗或界面刷新之后。

同一套资格函数供预览、提交与错误提示使用，差异只在信息详略。颜色显示“不可用”而提交仍成功，或预览允许但提交没有资格检查，都属于需核对的规则分叉。

稳定物品ID/当前实例与来源库存共同识别对象；列表下标、显示名称、历史指针和价格不是充分身份。组拖先明确成员快照、逐件数量与最终落点，再按操作ID去重；一帧内可以有多个合法操作，跨多帧也可能是同一次操作。

## 一次写入后的确认

能通过当前支持的原生/框架操作完成移动时，优先使用该入口。不要先手工摘源，再调用可能已经移动原物品的接受函数。

提交后核对返回值、实际余量、来源/目标归属和数量守恒；堆叠/拆分会改变对象身份，不能只看“原对象不在源里”。结果分为已确认成功、已确认拒绝、部分完成和结果不明。

写入抛异常不证明没有变更；读回失败也不证明失败。先记录已知状态并停止重复写，查清权威结果。不能为了让数量“对上”再调用另一接受入口、自动销毁源对象或补一次同样操作。

## 多步支付与交付

按当前API能力选择最简单的正确方案：

| 能力 | 实现选择 |
| --- | --- |
| 原生提供满足要求的完整交易 | 调用一次并确认其结果，避免重写原有副作用 |
| 可预留空间/资金/材料并可靠提交 | 先只读构建计划与预留，逐步提交；失败撤销本次已完成的步骤 |
| 只能部分交付或跨天履约 | 保存待交付余量、订单身份、已完成回执；后续按回执幂等履约 |
| 写入结果无法读取或可靠补偿 | 停止该操作并保留精确状态；先补足能力，不能承诺原子性 |

扣款、减库存、记订单是不同写入，事前全校验不使它们天然原子。逐步检查返回值；失败记录必须反映已经发生的变更。补偿本身失败时保留待处理状态，不能清空购物车/订单后只报一个错误。

奖励完成标记与交付顺序同样重要：不能先永久记完成再忽略发奖失败。部分交付按件/数量记回执，重载后核对剩余，而不是从头再发。

## 长任务与数值

批量整理、配装或布局搜索要设步数、内存与单帧预算；跨帧计划提交前核对输入版本仍相同。中途失效时丢弃计划并保持权威状态，别把过期位置写回。

金额、数量、容量、液体和概率明确单位、范围与溢出处理。生产基础价值、加工阶段、纯度修正和实际成交价分开；真实条件、用途类别、鉴定/伪装状态也分开，显示名称不能替代实际效果判定。

验证只选择受影响路径：满仓、形状不合、部分堆叠、重复回调、提交途中变化、扣款后失败、保存回退。静态可核对提交顺序和守恒条件，实际原生接受与保存结果需要对应运行验收。
